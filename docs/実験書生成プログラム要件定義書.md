# 実験プロジェクト：実験書・付録・PDF生成の設計方針

## 1. 目的

実験プロジェクトでは、現在Markdown形式（`.md`）で実験書を作成している。

実験書の最後には、実験で使用した**すべてのプログラム・設定ファイル等を付録として掲載する必要がある**。

ただし、実験中はプログラムを今後も変更する可能性があるため、実験書へコードを手作業でコピーするのではなく、

> **プロジェクト内の実ファイルを情報源（source of truth）とし、PDF生成時に自動的に付録へ埋め込む**

方式を採用する。

# 3. 基本方針

## 3.1 `docs/` とそれ以外を分離する

`docs/` は実験書・付録生成・PDF生成など、**ドキュメント作成専用のディレクトリ**とする。

したがって、`docs/` 以下のファイルは原則として付録には含めない。

例えば最終的には、

```text
/project
├── ...
├── include/
├── monitor/
├── src/
└── docs/
    ├── 実験書.md
    ├── 付録.md
    ├── exclude.txt
    ├── build.py
    └── ...
```

のような構成にする。

---

# 4. 付録対象ファイルの考え方

付録対象は「特定の拡張子のプログラムだけ」ではなく、

> **`docs/` を除くプロジェクト内のファイルを原則としてすべて付録対象とする**

という方針にする。ただし，これらは以下で示すexclude.txtで制御する．

したがって、以下も付録対象になる。

```text
platform.ini
setup.sh
setup.ps1
requirements.txt
include/*.hpp
src/*.cpp
monitor/*.py
```

将来的に、

```text
config.yaml
settings.json
README.txt
some_script.js
...
```

などが追加された場合も、原則として自動的に付録対象とする。

---

# 5. 除外ファイル・ディレクトリ

付録に含めたくないファイル・ディレクトリについては、

```text
docs/exclude.txt
```

にまとめて記述する。

例えば、

```text
# Git
.git
.gitignore

# PlatformIO
.pio/

# Python
__pycache__/
*.pyc

# IDE
.vscode/
.idea/
```

など。

---

# 6. `exclude.txt` の仕様

`exclude.txt` は、人間が編集する設定ファイルとする。

記法：

```text
# コメント

# ファイル・ディレクトリの指定
.git
.vscode/
.pio/

# ワイルドカード
*.pyc
*.tmp
```

最低限、

* コメント `#`
* ファイル名
* ディレクトリ
* ワイルドカード

を扱えるようにする。

---

# 7. `実験書.md` と `付録.md` を分離する

実験書本文と自動生成される付録は別ファイルにする。

```text
docs/
├── 実験書.md
└── 付録.md
```

## `実験書.md`

人間が編集する。

```markdown
# 実験書

## 1. 目的

...

## 2. 実験環境

...

## 3. 実験方法

...

## 4. 考察

...
```

コードは直接書かない。

## `付録.md`

**自動生成専用**。

人間は原則として編集しない。

---

# 8. `付録.md` の内容

付録には大きく2つを掲載する。

## 付録A：ファイル構成

プロジェクトのファイル構造を自動生成する。

例：

```text
project/
├── platform.ini
├── setup.sh
├── setup.ps1
├── requirements.txt
├── include/
│   ├── callbacks.hpp
│   ├── collision_avoidance.hpp
│   ├── config.hpp
│   └── ...
├── monitor/
│   ├── exp1_monitor.py
│   ├── exp2_monitor.py
│   └── exp3_monitor.py
└── src/
    ├── common/
    │   ├── espnow.cpp
    │   └── state.cpp
    ├── esp-now/
    │   └── main.cpp
    ├── monitor/
    │   ├── callbacks.cpp
    │   ├── logger.cpp
    │   └── main.cpp
    └── vehicle/
        ├── callbacks.cpp
        ├── collision_avoidance.cpp
        ├── controller.cpp
        ├── main.cpp
        ├── motor.cpp
        ├── prediction.cpp
        └── sensor.cpp
```

`docs/` と `exclude.txt` で指定された対象は表示しない。

---

# 9. 付録B：ソースコード

ファイル構造と同じ順番で、各ファイルの内容を自動的に掲載する。

例：

````markdown
# 付録

## A. ファイル構成

```text
project/
├── platform.ini
├── ...
````

## B. ソースコード

### B.1 `platform.ini`

```ini
...
```

### B.2 `setup.sh`

```bash
...
```

### B.3 `setup.ps1`

```powershell
...
```

### B.4 `requirements.txt`

```text
...
```

### B.5 `include/callbacks.hpp`

```cpp
...
```

...

````

ファイルごとに見出しを作り、コードブロックとして掲載する。

---

# 10. Markdownコードブロックの言語

ファイルの拡張子からMarkdownのコードブロック言語を自動判定する。

例えば、

| 拡張子 | コードブロック |
|---|---|
| `.cpp` | `cpp` |
| `.hpp` | `cpp` |
| `.c` | `c` |
| `.h` | `c` |
| `.py` | `python` |
| `.sh` | `bash` |
| `.ps1` | `powershell` |
| `.ini` | `ini` |
| `.yaml` | `yaml` |
| `.yml` | `yaml` |
| `.json` | `json` |
| `.txt` | `text` |

未知の拡張子については、`text` として扱う。

---

# 11. ファイル順序

ファイルはプロジェクトルートからの相対パスを基準にソートする。

例えば、

```text
platform.ini
setup.sh
setup.ps1
requirements.txt
include/callbacks.hpp
include/collision_avoidance.hpp
...
monitor/exp1_monitor.py
...
src/common/espnow.cpp
src/common/state.cpp
...
````

という順序。

これにより、

* ファイル構造
* 付録のファイル順
* 実際のプロジェクト構造

を一致させる。

---

# 12. PDF生成

PDF生成に必要なコードや設定はすべて `docs/` に置く。

例えば、

```text
docs/
├── 実験書.md
├── 付録.md
├── exclude.txt
├── build.py
└── ...
```

とする。

最終的な処理は、

```text
プロジェクト本体
        │
        ├── include/
        ├── monitor/
        ├── src/
        ├── platform.ini
        ├── setup.sh
        └── ...
                │
                ▼
          docs/build.py
                │
        ┌───────┴────────┐
        ▼                ▼
   実験書.md        プロジェクト探索
                        │
                        ▼
                   exclude.txt
                        │
                        ▼
                  付録.mdを生成
                        │
        ┌───────────────┘
        ▼
実験書.md + 付録.md
        │
        ▼
   PDF生成
```

とする。

---

# 13. 最終的なコマンド

理想的には、プロジェクトルートから、

```bash
python docs/build.py
```

だけ実行すればよいようにする。

この1コマンドで、

1. プロジェクトを探索
2. `docs/` を除外
3. `exclude.txt` を読み込む
4. 除外対象を除く
5. ファイル構造を生成
6. 対象ファイルの内容を読み込む
7. `docs/付録.md` を生成
8. `実験書.md` と `付録.md` を合成
9. PDFを生成

まで行う。

---

# 14. 重要な設計思想

## コードを二重管理しない

実際のコード：

```text
src/vehicle/controller.cpp
```

が唯一の正本。

`付録.md` にコピーされたコードは正本ではなく、**PDF生成のための自動生成物**とする。

したがって、

```text
controller.cppを変更
        ↓
python docs/build.py
        ↓
付録.md更新
        ↓
PDF更新
```

となる。

これにより、

> 実際に使用したコードと、実験書に掲載されたコードが食い違う

という事故を防ぐ。

---

# 15. `docs/付録.md` の扱い

`付録.md` は自動生成ファイルなので、人間が直接編集することは想定しない。

必要な変更は、

* `exclude.txt` を変更する
* ファイル構造を変更する
* `build.py` の生成ルールを変更する

ことで行う。

---

# 16. 今後実装するもの

次の順番で実装する。

### Step 1

`docs/exclude.txt` の仕様を決める。

### Step 2

プロジェクト全体を再帰的に探索する処理を作る。

* `docs/` は常に除外
* `exclude.txt` に指定されたものを除外
* ファイル・ディレクトリを取得
* シンボリックリンク等の扱いを決める

### Step 3

ファイル構造をMarkdown形式で自動生成する。

### Step 4

対象ファイルを読み込み、Markdownコードブロックに変換する。

### Step 5

拡張子からコードブロックの言語を判定する。

### Step 6

`docs/付録.md` を自動生成する。

### Step 7

`実験書.md` と `付録.md` を結合する。

### Step 8

Pandoc等を利用してPDFを生成する。

### Step 9

必要に応じて、

* 目次
* ページ番号
* 付録の改ページ
* コードの改ページ
* 日本語フォント
* PDFのタイトル・著者・日付
* コードのシンタックスハイライト

などを調整する。

---

# 17. 実装時の注意点

実験書として長期間使用するため、以下も考慮する。

* UTF-8で日本語ファイル名を扱えるようにする
* バイナリファイルを誤って読み込まない
* 巨大ファイルを必要に応じて除外できるようにする
* シンボリックリンクによる意図しないファイル探索を防ぐ
* `docs/` 以下を確実に除外する
* `exclude.txt` 自体も付録に含めない
* `付録.md` 自体も付録に含めない
* `build.py` 等のドキュメント生成用ファイルも `docs/` にあるため自動的に除外される
* 改行コードを適切に処理する
* ファイル名に日本語・空白が含まれていても処理できるようにする
* コード内にMarkdownのコードフェンス ``` が含まれる場合の扱いを考える
* PDF化した際に長いコード行がはみ出さないようにする
* 大量のコードを含む場合のページ分割を考慮する

---

# 18. 目標

最終的には、

```bash
python docs/build.py
```

を実行するだけで、

```text
実験プロジェクト
      ↓
対象ファイル自動検出
      ↓
ファイル構造自動生成
      ↓
ソースコード自動取得
      ↓
付録.md自動生成
      ↓
実験書.md + 付録.md
      ↓
PDF
```

という完全に再現可能なドキュメント生成環境を構築する。

**実験書本文は `docs/実験書.md`、実験に使用したコード・設定ファイルはプロジェクト本体、付録は自動生成**という3者分離を基本とする。

# 19. testディレクトリの例外処理
test/ は学生向けの穴埋め課題用ファイルを格納する特殊ディレクトリである。

test/ 自体は付録対象外。
ファイル構造の自動生成にも含めない。
exclude.txt に記載する必要はない。
test/ 内にあるファイルは直接付録へ掲載しない。
付録対象となるファイル X に対して test/X が存在する場合、X の内容として test/X を使用する。
test/X が存在しない場合は、元の X を使用する。
test/ にのみ存在するファイルは付録対象としない。
test/ 内のディレクトリ構造は、プロジェクト本体と同じ相対パス構造を想定する。
これにより、学生向け実験書には完全版コードではなく、穴埋め版コードが掲載される。
